# Building jamovi modules

jamovi's own documentation (<https://dev.jamovi.org>) teaches the happy path well and
you should follow it. This skill covers what it does not: behaviour that is
**undocumented, silent, or contradicts the docs**, each claim carrying the
file:line or measurement that proves it, so you can re-verify instead of trusting.

**Verified against jamovi 28.1.0.0, jmvtools 28.3 (jamovi-compiler 0.3.5),
jmvcore 2.7.38, on 2026-08-05.** Re-check anything load-bearing against the
target version — `references/docs-and-source-map.md` says how.

## Before you write code

1. **Check whether the answer already exists.** Read `references/traps.md`
   (one-line checklist) end to end — it is 60 seconds and most of the expensive
   bugs below are on it.
2. **Get the source, not just the docs.** Clone `jamovi/jamovi` and keep it
   beside the module. Every claim here is checkable there in a minute, and the
   docs lag the code in both directions. `references/docs-and-source-map.md`
   maps which questions are answered by which file, and `scripts/mirror-jamovi-docs.sh`
   pulls a local, greppable copy of dev.jamovi.org.
3. **Measure before designing** if the module moves real data. Three hard
   ceilings sit between the browser and R, all of them fail silently, and one of
   them (results ≈ 3M cells) has already forced an architecture change on us. A
   day of benchmarking answered them; guessing did not. See `references/data-io.md`.

## The shape of a module

```
MyModule/
├── DESCRIPTION            # an ordinary R package; Imports:, License:, Version:
├── NAMESPACE
├── R/
│   ├── myanalysis.h.R     # GENERATED by jmvtools::prepare — never edit
│   ├── myanalysis.b.R     # the R6 backend: .init(), .run(), .plot()
│   └── *.R                # pure compute, flat — R CMD INSTALL does not recurse
├── jamovi/
│   ├── 0000.yaml          # module metadata (GENERATED from the .a.yamls)
│   ├── 00refs.yaml        # references — needs a top-level `refs:` key
│   ├── myanalysis.a.yaml  # options
│   ├── myanalysis.r.yaml  # results structure
│   ├── myanalysis.u.yaml  # options-panel layout
│   └── js/myanalysis.js   # optional options-panel behaviour
├── data/                  # optional bundled datasets, registered in 0000.yaml
└── tests/testthat/
```

**Name every file in `jamovi/` in lower case, whatever the analysis is called.**
`name: snpImport` lives *inside* the yaml; the files are `snpimport.*`. The
compiler names its output from the file basename (`index.js:411-419`) while the
server only ever serves `ui/<analysis_name.lower()>.js`
(`server/jamovi/server/server.py:426`, from `client/main/optionspanel.ts:186`).
Get this wrong and on Linux the panel still renders from the `.u.yaml` while
**every injected control silently vanishes** — the JS 404s and no handler runs.
macOS hides the bug completely. jmv does the same (`name: contTables` ships as
`conttables.js`).

## The eight rules that cost the most to learn

1. **A table's rows and columns must exist by the end of `.init()`.** jamovi
   builds a fresh analysis object on every option click and restores the previous
   results into it; `Table$fromProtoBuf` walks the rows *that exist now*
   (`jmvcore/R/table.R:736`) and matches them into the incoming message by name.
   Anything created in `.run()` is never restored, so every click renders the
   table empty and then refills it. Create structure in `.init()`, write values
   with `setRow()` in `.run()`.
2. **Therefore `tbl$rowCount` is not a "did I already do this?" guard.** If rows
   are added in `.run()` it is always 0 there. Cache the *computation* instead —
   `Table$setState()`/`$state`, cleared by the same `clearWith`.
3. **`Table$addRow` is O(n²)** — it re-serialises every row name on every call
   (`jmvcore/R/table.R:371`). 500 rows = 5.4 s; 2016 rows = 41 s. And because
   rows must be built in `.init()`, that cost is paid **on every checkbox click**.
4. **`clearWith` defaults to `*`** — "clear on any option change". An
   instructions panel or a note with no explicit `clearWith` is wiped by every
   click. Conversely, an option your render function reads but that is *absent*
   from an Image's `clearWith` silently does nothing.
5. **Three transport ceilings, 1–4 MiB, all silent.** Nothing is logged, no
   error reaches R, the analysis just never returns — or worse, renders its
   tables from the last progressive send with the data columns missing, so it
   looks like it worked.
6. **There is no File option and no file picker.** Files enter through injected
   JavaScript that reads bytes in the browser into a hidden `String` option. A
   path option is the wrong answer and will not survive review.
7. **An analysis cannot register a file format, delete a column, or write into
   an existing one.** It can only create output columns — which *can* grow the
   dataset's row count, and that is what makes importer-style analyses possible.
8. **`jmvtools::install()` reports failure on stdout and still exits 0.** It has
   printed `Module installed successfully` having installed nothing. Check the
   module directory, never the exit status.

## Working style that paid off

- **Keep compute free of jmvcore.** Parsers and statistics in plain functions
  with no R6, no `self`, no file access; the backend only orchestrates. It is
  the difference between a testable module and a UI you have to click.
- **Two test layers.** Oracle tests recompute every result a second way (base R,
  or an outside tool) and catch logic regressions; golden tests pin captured
  numbers and catch the R/package upgrade that shifts them. Never hand-write a
  golden value.
- **Run the panel JS, do not only read it.** A Load button has shipped dead
  twice here — once from a throw while building it, once from a stray
  identifier. Only a test that injects the panel and clicks sees that.
- **Regenerate the generated files in CI and fail if the tree is dirty.**
  `.h.R`, `00jmv.R` and `0000.yaml` are committed and go stale otherwise.
